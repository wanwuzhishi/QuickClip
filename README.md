# QuickClip

高性能 Windows 剪切板管理器。基于 **Tauri 2 + Rust + TypeScript** 构建，常驻系统托盘，通过全局快捷键唤出紧凑面板，支持文本、图片、文件、富文本四类内容的采集与回填。

[![License: MIT](https://img.shields.io/badge/License-MIT-blue.svg)](LICENSE)

> 数据层采用泛化的 KV + JSON 文档存储方案：条目主体是一份 JSON 文档，
> 检索与排序所需的高频字段（指纹、类型、时间戳等）拆成独立的按列存储，
> 从而在不引入关系型数据库的前提下兼顾灵活性与查询效率。

## 界面设计

界面采用 **Apple Human Interface Guidelines** 的视觉语言，深色为默认，可在设置中切换浅色。

| 元素 | 设计对应 |
|---|---|
| 窗口圆角 | 14px，配 0.5px 细边框模拟 macOS 窗口 |
| 顶部工具栏 | 左侧标签分段控件；右侧四个操作按钮（固定 / 搜索 / 设置 / 关闭），**悬停才浮出底色**，静止时视觉极简 |
| 拖动区域 | 标题栏中部留白为拖拽热区；标签与按钮本身不参与拖动 |
| 关闭按钮 | 位于按钮组最右，前有细分隔线与「设置」隔开；用 CSS 画 × 号而非文字符号；悬停转淡红底（Windows 关闭键的既有心智）。设置面板头部的关闭按钮共用同一套画法与悬停反馈 |
| 标签切换 | macOS 分段控件（选中项为浮起白色滑块 + 微投影） |
| 列表选中 | 系统强调色填充（深色 `#0A84FF` / 浅色 `#007AFF`），非描边 |
| 设置面板 | iOS 分组式表单：大写灰色分组标题 + 白底圆角卡片 + 内部细分割线 |
| 快捷键录入 | 点击后直接按键，自动识别组合（见下节） |
| 布尔开关 | iOS 开关，滑块采用带过冲的弹性缓动 |
| 右键菜单 | 半透明材质（`backdrop-filter` 毛玻璃）+ 强调色悬停 |
| 字体 | 优先 SF Pro / PingFang SC，Windows 回退 Segoe UI Variable / 微软雅黑 |

> **顶部按钮的演变**
>
> 1. **红绿灯圆点**：最初用 macOS 红绿灯承载全部操作（红=隐藏、黄=设置、绿=搜索）。
>    圆点只能靠颜色和悬停符号区分，含义全靠猜，用户反馈**根本找不到设置入口**。
> 2. **胶囊按钮**：改为图标 + 文字标签，一眼可辨。但带底色又占地方，
>    用户反馈**标题栏可拖动区域太小**。
> 3. **去底色 + 拖拽留白**：按钮去掉常态底色（悬停才浮出），标签在窗口变窄时
>    自动收起，并在标签与按钮之间留出**专用于拖动**的弹性空白区。
>    这一轮顺手把「隐藏面板」降级为标题栏双击与 `Esc`——当时判断它不是高频操作。
> 4. **关闭按钮加回来**：实践发现可发现性终究无可替代，用户找不到隐藏入口。
>    此次动了配套布局：放在按钮组最右侧、前置一条分隔线避免与「设置」误点，
>    同时把按钮内边距 6→5px、间距 3→2px、标签收起阈值 340→360px，
>    **把多出来的宽度从按钮自身挤出来，拖拽区宽度保持不变**。
>    关闭按钮与标题栏双击并存：前者是看得见的入口，后者是老手的快捷方式。

配色取自 Apple 系统色板：强调色为 systemBlue，语义色为 systemRed / systemGreen / systemYellow。所有圆角、缓动曲线集中定义在 `src/styles.css` 顶部的 CSS 变量中，便于整体调节。

> 设计预览文件位于 `.workbuddy/preview/apple-ui-preview.html`，可在浏览器直接打开查看深色 / 浅色 / 设置面板三态。

## 快捷键录入

**不需要手工拼写 `Alt+V`**。在设置里点击「唤出快捷键」，按钮进入监听态（描边高亮 + 呼吸动画），
此时**直接按下你想要的组合键**即可，界面立即回显识别结果。

- 按下修饰键时会实时预览（如 `Ctrl+Shift+…`）
- 必须有至少一个修饰键（Ctrl / Alt / Shift / Win），否则会劫持普通按键输入，界面会提示
- `Esc` 取消录入
- 识别结果会写入配置，但**要点「完成」才真正保存并重新注册**；注册失败（被占用）会明确报错且不保存

支持的键：字母 `A-Z`、数字 `0-9`、`F1-F12`、方向键、`Space`、`Enter`、`Tab`、`` ` ``、`-`、`=`、
`[`、`]`、`\`、`;`、`'`、`,`、`.`、`/`。

### 关键设计决策

**1. 序列号轮询而非钩子采集**

通过 `GetClipboardSequenceNumber` 以 200ms 间隔检测剪贴板变化。相比挂钩子方案，无需注入其他进程，不会触发杀软误报，稳定性显著更优。

**2. 泛化 KV + JSON 文档存储**

主表结构统一为 `Id(PK) + UpdateTime + Data(JSON) + ObjectType + CreatedTime`。新增对象类型无需变更表结构，扩展成本接近零。

**3. 内存缓存优先**

启动时全量加载到内存（`db::Cache`），运行期读取全部命中内存，SQLite 仅承担持久化职责。列表渲染响应在毫秒级。

**4. 粘贴去自触发**

应用自身写回剪贴板时设置 `suppress` 标志，轮询线程据此跳过该次变更，避免"复制→采集→再复制"的无限循环。

**5. 焦点接力（无焦点粘贴的实现关键）**

粘贴失败最常见的原因是**焦点丢失**——投递的按键只会送到当前拥有焦点的窗口。
完整链路为：

```
唤出面板前 ──► 记录当前前台窗口句柄 (LAST_FOREIGN_FOREGROUND)
               （由 SetWinEventHook 持续维护，非唤出时刻临时抓取）
                        │
用户单击/回车 ──► 焦点是否已在目标？
                  ├─ 是 ──► 跳过抢占（不夺焦点模式的常态）
                  └─ 否 ──► force_foreground(target_hwnd)
                              └─ AttachThreadInput + SetForegroundWindow
                        │
                        ▼
                   等待焦点落定 ──► 校验焦点已到位 ──► 投递 Ctrl+V
                   （40ms / 150ms）
```

`force_foreground` 内部先用 `AttachThreadInput` 把当前线程的输入队列挂接到目标窗口线程，再调用 `SetForegroundWindow`，最后解除挂接。这是绕过 Windows「非前台进程不得抢占前台」限制的可靠做法。

**为什么不夺焦点模式下要跳过抢占**：面板自始没拿焦点，焦点一直在目标窗口，
此时再调 `force_foreground` 会重新触发一次激活流程，反而打乱目标输入框的状态。

若记录到的窗口属于本进程自身（例如面板刚被点击过），则不覆盖已有记录，避免把粘贴目标错设为自己。

**6. 快捷键运行时重绑定**

修改快捷键后必须注销旧键、注册新键。`rebind_hotkey` 的顺序是**先注册新键、成功后才卸旧键**；前端在保存设置时若检测到快捷键变更，会先调用它并确认成功，**成功后才落盘配置**——避免出现"配置已存但快捷键没生效"的不一致状态。

> **为什么必须是这个顺序**：早先的实现是「先 `unregister_all()` 再注册新键」。
> 那会留下三条都会让用户**彻底失去全局快捷键**的失败路径——新组合被占用、
> 新字符串无法解析、新值为空。三种情况下旧键都已被注销，界面却只显示一条
> 注册失败，用户完全看不出快捷键已经没了，连面板都再也唤不出来。
>
> 现在的顺序下，任何一步失败都保持旧键可用，最坏情况只是「这次修改没生效」。

**7. 托盘完全由代码托管**

托盘图标与右键菜单在 `main.rs` 中通过 `TrayIconBuilder` 构建，**不在 `tauri.conf.json` 中声明 `trayIcon`**。

原因：配置文件里的静态 `trayIcon` 会被 Tauri 在启动时自动创建，它无法挂载菜单与事件回调。若同时存在配置托盘与代码托盘且 id 相同，两者会冲突——实际生效的往往是那个**没有菜单**的配置托盘，表现为「右键没有任何选项」。

另外托盘对象必须由具名变量持有并 `app.manage(tray)` 托管。若写成 `let _tray = ...`，对象会在 `setup` 闭包返回时被 drop，托盘图标与菜单一并消失。

**8. 开机自启与静默启动**

自启由官方 `tauri-plugin-autostart` 插件实现，写入当前用户的系统启动项（无需管理员权限）。

关键设计：插件在 `init` 时需**静态声明**启动参数，本项目传入 `--silent`：

```rust
tauri_plugin_autostart::init(MacosLauncher::LaunchAgent, Some(vec!["--silent"]))
```

启动判定极简，**只看一个命令行参数**：

```
命令行含 --silent（本程序写入的启动项才会带） ──► 开机自启
                                                 ├─ startMinimized 开 → 静默驻留托盘
                                                 └─ startMinimized 关 → 弹出面板
命令行无该参数 ────────────────────────────────► 手动启动 ──► 必定显示面板
```

**手动启动必须先出现窗口。** 这是明确的交互约定：用户双击图标后若毫无反应（只有托盘多出一个图标），会被直接判断为"软件没打开"。

`--silent` 由本程序通过 `tauri_plugin_autostart::init` 静态写入启动项，**只有开机自启会带上**，因此它是区分两种启动来源的唯一可靠依据。

> **不要试图用"父进程是不是 explorer.exe"来区分。**
> 用户手动双击图标时，父进程**同样是 explorer.exe**，两者无法靠父进程名区分。
> 曾据此做过"参数缺失时的兜底"判断，结果在 `startMinimized` 默认为 `true` 时
> 把手动启动也静默掉了——正是"双击没反应"这个 bug 的第二次复发。
> 该兜底逻辑与其配套的 `parent_process_name()` 已全部删除。

**为什么用命令行参数而非只读配置**：自启场景应静默——用户开机时不该被弹窗打扰。用参数可让"自启行为"与"手动启动行为"独立，两者共用同一份配置。用户若希望开机自启时也弹窗，把设置里的「开机自启时静默到托盘」关掉即可。

**状态以系统为准**：`get_autostart` 查询的是注册表实际状态而非配置文件。用户可能通过任务管理器禁用启动项，此时配置会与事实不符。启动时也会自动同步一次，修正偏差。

## 数据目录

运行时数据位于 `%APPDATA%\com.quickclip.app\`：

```
com.quickclip.app/
├── userdata.db              # SQLite 主库
├── quickclip.log            # 运行日志（每次启动截断重写）
├── Configs/
│   └── ClipConfig.json      # 用户配置（可手工编辑）
└── Image/                   # 图片类型内容的落盘目录
```

> `quickclip.log` 记录启动参数、快捷键注册结果、静默启动判定等关键状态。
> 排查「开机自启是否生效」「快捷键为何没反应」这类无法直接观察的行为时，先看它。

> **日志初始化先于数据迁移**：迁移过程本身要写日志（迁没迁、走了哪条路径、
> 失败原因），否则老数据没跟上来时只能看到空文件。早期顺序相反，
> 迁移日志全部丢失，这也是该顺序固定的原因。

> **图片以数据目录为基准寻址**：`Image/` 下的文件在库里只存相对路径，
> 读取时拼上数据目录还原。绝不能用进程当前工作目录——它取决于用户从哪启动
> （快捷方式、安装目录、资源管理器双击各不相同），基准一旦错位，
> 表现就是「历史里有图片条目，点粘贴却报读取失败」。

> **图片文件名带随机后缀**：命名规则为 `时间戳_短随机ID.png`。
> 随机后缀不是可选的——只用毫秒时间戳时，快速连截两张图只要落在同一毫秒，
> 后一张就会覆盖前一张，表现为「历史里少了一条，且剩下那条内容不对」。

### 从 ClipForge 迁移

本项目原名 **ClipForge**，应用标识符为 `com.clipforge.app`；现更名 **QuickClip**，标识符为 `com.quickclip.app`。

由于 Tauri 的数据目录由标识符决定，改标识符会导致数据"换位置"。为了让老用户无感升级，**首次启动时会自动搬迁旧数据**：

```
%APPDATA%\com.clipforge.app\  ──►  %APPDATA%\com.quickclip.app\
```

迁移规则（保守优先，宁可不动也不误删）：

- **仅在新目录不存在或为空时迁移**——避免覆盖你改名后产生的新数据；
- 优先**整体重命名目录**（同盘符下是原子操作，快且不留冗余副本）；
- 若重命名失败（跨盘符、被占用等），退化为**递归复制**，且**保留旧目录**让你有兜底；
- 迁移过程与结果都会写入 `quickclip.log`。

> 若你不需要旧数据，直接删除 `%APPDATA%\com.clipforge.app\` 即可。
> 注意旧版的开机自启注册的是 `clipforge.exe`，升级后请在设置里**重新打开一次「开机自启」**，
> 让系统启动项指向新的 `quickclip.exe`。

## 开发

### 环境要求

- Node.js ≥ 18
- Rust ≥ 1.77（MSVC 工具链）
- Visual Studio C++ 生成工具
- WebView2 运行时（Windows 10/11 通常已预装）

### 从源码构建

```bash
git clone https://github.com/wanwuzhishi/QuickClip.git
cd QuickClip
npm install
npm run tauri:dev     # 开发模式（热重载）
```

### 命令

```bash
npm install          # 安装前端依赖
npm run tauri:dev    # 开发模式（热重载）
npm run tauri:build  # 构建发布版（NSIS 安装包）
npm run pack:test    # 打包测试版（自动递增版本号，产物归集到 dist-release/）
```

构建产物位于 `src-tauri/target/release/bundle/nsis/`。

### 测试版打包

每次代码变动后执行 `npm run pack:test`。该脚本会：

1. 自动递增 patch 版本号（`0.1.N` → `0.1.N+1`），并同步写入 `package.json` 与 `tauri.conf.json`
2. 物理清空 `dist/`，再交给 Tauri 完成「前端 + Rust + NSIS 安装包」的完整构建
3. 把产物归集到 `dist-release/`，文件名统一为 `QuickClip_v<版本>-test.<时间戳>_<类型>.exe`
4. **清理旧产物，只保留最近 3 个版本**
5. 生成 `build-info.txt` 记录构建时间与产物清单

> **为什么第 2 步要手动清 `dist/`**：Vite 的 `prepareOutDir` 用 `fs.rmSync` 清空输出目录，
> 在带 safe-delete shim 的宿主环境里会被代理成"移入回收站"，该调用可能超时
> （`ETIMEDOUT`）而使整个构建失败。`dist/` 本是构建产物、无需保留，物理删除可绕开。
> 另外脚本**不单独跑 `npm run build`**——`tauri build` 的 `beforeBuildCommand`
> 本来就会构建前端，重复执行等于构建两遍，且会再次触发上述清空路径。

产物说明：

| 文件 | 用途 |
|---|---|
| `QuickClip_*_portable.exe` | 免安装版，双击直接运行 |
| `QuickClip_*_setup.exe` | NSIS 安装包，含开始菜单与卸载项 |
| `build-info.txt` | 本次构建的版本、时间与产物清单 |

**只保留 3 个版本**是为了避免 `dist-release/` 无限堆积。清理按版本号分组，
同一版本的 portable 与 setup 一起删除，不会留下不配套的组合。
如需保留更多，用环境变量覆盖：`KEEP_VERSIONS=5 npm run pack:test`。

> 版本比较用的是 `sort -V`（版本序）而非字符串序——字符串序下
> `0.1.9` 会排在 `0.1.10` 之后，导致 0.1.10 / 0.1.11 被当成旧版本误删。

## 快捷键

| 按键 | 行为 |
|---|---|
| `Alt+V` | 唤出 / 隐藏面板（可配置） |
| `↑` / `↓` | 移动选中项 |
| `Enter` | 粘贴选中项 |
| `Ctrl+Enter` | 以纯文本粘贴 |
| `1` ~ `9` | 直接粘贴第 N 项 |
| `Delete` | 删除选中项 |
| `Esc` | 清空搜索 / 隐藏面板 |
| 直接输入字符 | 自动聚焦搜索框 |

> **⚠ 前提：面板需先有键盘焦点。**
> 默认开启「唤出时不抢焦点」（见「粘贴的焦点问题」），面板弹出时**不夺取焦点**，
> 因此上表中的方向键、数字键、`Enter` 等**要先点一下面板**才会响应。
> 这是刻意的取舍：不夺焦点才能保住目标程序的输入框。
> 点面板任意空白处即会聚焦搜索框（后端起临时脱掉 `WS_EX_NOACTIVATE` 样式），
> 之后键盘操作全部可用；搜索框失焦后样式会自动戴回。
> 若你更习惯"唤出即可直接打字搜索"，把设置里的「唤出时不抢焦点」关掉即可。

> **关于快捷键冲突**：默认值从 `Alt+Space` 改为 `Alt+V`，因为 `Alt+Space` 是 Windows 保留的「窗口系统菜单」快捷键，注册必定失败。若你自定义的组合也被其它程序占用，设置面板会明确提示且**不会保存**（避免出现「界面显示已改、实际没生效」的假象），此时换一个组合即可。

## 窗口固定

右上角图钉按钮切换两种交互模式：

| 状态 | 行为 |
|---|---|
| **未固定**（默认） | 单击条目 → 粘贴一次 → 面板自动关闭。适合"快速取值就走" |
| **已固定** | 窗口保持最上层，粘贴后**不关闭**，可连续往同一目标粘贴多条 |

实现要点：

- 固定状态由后端 `AppState.pinned` 持有，**不写入配置文件**——它是本轮的交互意图，不是需要跨会话保留的长期偏好，每次启动都从未固定开始。
- **固定状态在"隐藏 → 再唤出"之间保持不变**。关闭按钮、标题栏双击、`Esc`、全局快捷键都只隐藏面板，不改动 `pinned`；再次唤出时 `show_panel` 读到的仍是固定状态，并会把面板重新提到最上层。
- 唤出时补设置顶用**两层保险**：先走框架 `set_always_on_top(true)`，再用原生 `is_topmost()` 读系统真实样式，若发现掉了就 `SetWindowPos(HWND_TOPMOST)` 补一次。原因是 hide/show 循环、外部程序改 Z 序都可能让窗口脱离 topmost，而**框架的内部状态标记不会跟着更新**——只信框架会得到"以为还置顶、实际已取消"的假象。
- 所有粘贴路径（单击、回车、数字键、右键菜单）都汇入同一个 `paste_to_active`，因此固定逻辑只需在那一处判断，行为天然一致。
- 固定时粘贴同样**不会去抢焦点**：唤出时既然没夺走焦点，粘贴时也就不必抢回来（详见下节）。
- 固定状态会**豁免"失焦即隐藏"**（`hideMode=1`）：固定即常驻，若点一下别处就消失，与固定的语义相矛盾。
- 全局快捷键与关闭按钮仍可随时隐藏面板——那是用户的明确意图，不受固定影响。

> **置顶状态的判定以系统为准**：`set_pinned` 的返回值取自 `WS_EX_TOPMOST`
> 扩展样式的实际值，而非我们写入的意图值。以管理员身份运行时，普通的
> `set_always_on_top(false)` 会被系统忽略，此时必须用
> `SetWindowPos(HWND_NOTOPMOST)` 显式降级。

## 窗口定位

面板每次显示前会按配置策略重新计算位置，可在设置 →「窗口行为」中切换。

| 策略 | 行为 |
|---|---|
| **跟随鼠标**（默认） | 在鼠标右下方 8px 处弹出；空间不足则翻到左上方 |
| **上次关闭位置** | 沿用上次隐藏时的坐标；首次运行（无记录）退回跟随鼠标 |
| **固定位置** | 使用设置里填写的 `fixedX` / `fixedY` |

实现要点：

- 定位发生在 `show()` **之前**（`apply_window_position`），否则用户会看到窗口先出现在旧位置再"跳"过去。
- **越界时翻转而不是钳制**：右下方空间不够就把窗口放到鼠标左上侧。直接钳进屏幕会让窗口紧贴边缘、脱离鼠标，"就近弹出"的意义就没了。只有在翻转后依然越界（鼠标贴在最左上角等极端情况）才退化为钳制。
- 所有坐标计算都在**物理像素**下进行（`GetCursorPos` + `MonitorFromPoint` 取工作区），与 `PhysicalPosition` 一致，避免 DPI 缩放导致的偏移。
- 边界用的是鼠标所在显示器的**工作区**（`rcWork`）而非整屏尺寸，这样贴边弹出不会被任务栏盖住。
- `lastX` / `lastY` 在 `hide_panel` 中自动记录；`fixed_x` / `fixed_y` 由用户填写。**两者分开存放**——若共用一个字段，切换策略时会互相覆盖。
- 若当前策略是 `fixed`，用户手动拖走窗口后新坐标也会被采纳（写回 `fixedX` / `fixedY`），下次不会又跳回旧位置。
- 坐标输入框只在选中「固定位置」时显示，避免误以为它会影响到其它模式。

## 粘贴的焦点问题

这是剪贴板管理器最容易出错、也最容易被误判为"软件有 bug"的地方。当前实现分三层：
**目标的确定**、**唤出时永不抢焦点**、**粘贴时按需交还焦点**。

### 一、粘贴目标用什么确定

**旧做法（已废弃）**：在 `show_panel` 里临时抓一次前台窗口。
问题在于调用时机不可靠——面板可能刚被鼠标点过、或上一次隐藏尚未生效，
此时抓到的"目标"其实是面板自己或一个瞬时窗口，粘贴自然无从谈起。

**新做法（当前）**：安装 `SetWinEventHook` 监听 `EVENT_SYSTEM_FOREGROUND`，
**持续追踪**前台变化，记录"用户最后一次真正在用的非自身窗口"（`platform::LAST_FOREIGN_FOREGROUND`）。
记录与实际唤出时机无关，因此天然正确。

- 使用 `WINEVENT_OUTOFCONTEXT | WINEVENT_SKIPOWNPROCESS`：回调在本地线程执行，
  无需注入目标进程，稳定且不会被杀软拦截。
- 过滤掉工具窗口、无标题窗口、输入法等辅助窗口（`is_real_top_level`），
  避免把不存在的东西记成粘贴目标。
- 这一思路参考了成熟开源剪贴板管理器（EcoPaste 等）的实现。

### 二、唤出时不抢焦点（`showWithoutActivating`）

**要解决的现象**：粘贴到输入框时，输入框在按快捷键的瞬间就关闭了，于是什么都没粘上。

**根因**：许多目标程序的输入框是"**失焦即关闭**"的——

- 浏览器地址栏的联想下拉、页面内搜索条
- 编辑器命令面板（VS Code `Ctrl+Shift+P` 等）
- 聊天软件输入框的 @ 提及浮层
- 各类网站搜索 Suggestions 列表

面板为接收用户的按键输入，常规做法是 `set_focus()` 抢走前台焦点。
于是用户按下 `Alt+V` 的一瞬间，**目标输入框先因失焦被销毁**；等面板粘贴时
把焦点还回去，那个输入框早就不存在了，Ctrl+V 落到窗口本体上——
用户看到的就是"输入框没了，也没粘上"。

**解法**：给面板打上 `WS_EX_NOACTIVATE` 扩展样式，让它在系统层面**永远无法成为前台窗口**。
这不是"显示时不激活"（`SWP_NOACTIVATE` 只管一次调用，用户点一下窗口照样会被激活），
而是**持久的窗口属性**：面板从生到死都当不了前台，目标输入框全程保持焦点，
粘贴时**根本不需要任何焦点转交**。

实现分三块，缺一不可：

**① 窗口样式**（`platform::set_no_activate`）

```rust
let cur  = GetWindowLongPtrW(hwnd, GWL_EXSTYLE) as u32;
let want = if no_activate { cur | WS_EX_NOACTIVATE.0 }
                          else { cur & !WS_EX_NOACTIVATE.0 };
SetWindowLongPtrW(hwnd, GWL_EXSTYLE, want as isize);
// 改扩展样式后必须发一次 SWP_FRAMECHANGED 让系统重新评估
SetWindowPos(hwnd, None, 0, 0, 0, 0,
    SWP_NOMOVE | SWP_NOSIZE | SWP_NOZORDER | SWP_NOACTIVATE | SWP_FRAMECHANGED)
```

- **顺序很重要**：必须在 `show()` **之前**打样式。先显示再改样式，中间那一瞬
  窗口仍会短暂抢一下焦点，输入框可能已经关了。
- 样式在 `hide_panel` 中**恢复**，避免影响下次非该模式下唤出。

**② 搜索框的临时可聚焦**

`WS_EX_NOACTIVATE` 的窗口永远拿不到键盘焦点，搜索框也就没法打字——
这是本路线的**固有代价**。唯一解法是"要输入时临时脱掉样式、输入完戴回去"：

```
点击搜索框 / 按下字符键 ──► set_search_focusable(true)   （去掉 NOACTIVATE）
搜索框失焦 / 关闭搜索   ──► set_search_focusable(false)  （戴回 NOACTIVATE）
```

> **必须先 `await` 后端改完样式，再调 `$search.focus()`。**
> 顺序颠倒的话，前端在窗口还是 NOACTIVATE 状态时就尝试聚焦，
> 浏览器会拒绝把该 document 设为活动文档，聚焦静默失败。

**③ 点窗外隐藏（全局鼠标钩子）**

NOACTIVATE 窗口**收不到 `WM_KILLFOCUS` / `WM_ACTIVATE`**，
原先靠 `blur` 实现的"点别处就收起"彻底失效，必须自己实现。
方案是装一个 `WH_MOUSE_LL`（低级鼠标钩子）：

- 钩子回调拿到点击坐标，用 `GetWindowRect` 判断是否落在面板矩形外；
  是则置一个"请求隐藏"的原子标志。
- **低级钩子的回调运行在安装它的那个线程的消息循环里**，因此必须为该线程
  跑一个 `GetMessageW` 泵，否则钩子收不到任何事件。
- 不注入任何进程、无需 DLL，对杀软友好；回调必须调用 `CallNextHookEx` 放行。
- 钩子线程不能直接调 Tauri API（那些要求主线程），所以用
  **标志位 + 前端轮询**（200ms）而非事件投递——这个动作频率极低，轮询开销可忽略，
  换来实现上的简单可靠。
- 可见性判断放在**后端**：`poll_hide_request` 内部先用 `is_visible` 检查窗口，
  不可见就直接返回 `false` 且**不消费**标志。前端拿不到可靠的窗口可见性
  （`document.hidden` 反映的是页面可见性，Tauri 的 `hide()` 不保证让它变化）。
- 固定状态与设置面板打开时豁免（与 `blur` 逻辑一致）。

> 若不需要这个行为，可在设置 →「窗口行为」→「唤出时不抢焦点」关闭，
> 退回旧的抢焦点模式（适合"总是先搜索再粘贴"、不介意输入框关闭的场景）。

### 三、粘贴时按需交还焦点

**Windows 的硬性限制**：只有**当前持有前台焦点**的进程，才有资格把前台
转交给别的窗口。而面板若抢走了前台焦点，孤立的 `SetForegroundWindow`
会被系统静默忽略，表现为"点了没反应"。

**解决顺序**（`platform::force_foreground`）：

1. `AttachThreadInput` 把本线程与目标线程的输入队列临时合并，使本线程
   在系统看来"就是"前台线程，此时 `SetForegroundWindow` 才会被接受。
2. 仍失败则 `ShowWindow(SW_MINIMIZE)` + `SW_RESTORE`，强制窗口管理器
   重走一次激活流程，绕过前台锁。
3. 最后 `BringWindowToTop` + `SetForegroundWindow` 兜底。

**关键：抢焦点是"焦点被夺走了"才需要的补救，焦点没丢就不该去碰。**

不夺焦点模式下面板自始没有前台焦点，焦点一直在目标窗口。此时若还去调
`force_foreground`，虽然目标已是前台、函数立刻返回成功，但"抢占焦点"这个
动作本身会在部分程序里重新触发一次激活流程，反而把输入框的焦点状态搅乱
（联想下拉重新弹出、命令面板重启）。因此 `paste_to_active` 先判断
`foreground_window() == 目标`，已是前台就跳过抢占。

**动作顺序**（`paste_to_active`）：

```
1. 判断焦点是否已在目标窗口
   ├─ 已在 → 跳过抢占（不夺焦点模式的常态）
   └─ 不在 → 抢焦点（趁面板还是前台，此时才有转交资格）
2. 隐藏面板（固定状态下跳过，保持常驻）
3. 等待焦点落定
   · 焦点本就未丢 → 40ms（没有窗口切换要等，只留给目标处理剪贴板写入）
   · 需要抢占    → 默认 150ms，可在设置中调整「粘贴延迟」
4. 焦点未到位则重试，最多 3 轮、逐轮加长等待
5. 确认焦点已到位 → 投递 Ctrl+V
```

早期实现把"隐藏面板"放在第 1 步，在目标程序响应较慢时，面板的隐藏动画
与目标窗口的激活互相竞争，`SetForegroundWindow` 往往被拒绝，按键就投递
给了焦点悬空的窗口。

**第 5 步的校验不可省**：如果焦点没到位就投递按键，Ctrl+V 会落到当前持有
焦点的任意窗口上，造成**误输入**——这比"粘贴失败"更糟。因此此时宁可直接
放弃本次粘贴，并在日志中记录原因（`%APPDATA%\com.quickclip.app\quickclip.log`）。

**按键投递用 `SendInput` 而非 `keybd_event`**：前者可一次提交完整按键序列，
且能正确携带扫描码，对 Electron / WPF / UWP 等对 `WM_KEYDOWN` 的 `lParam`
较真的程序兼容性更好。序列固定为 `Ctrl↓ V↓ V↑ Ctrl↑`；
**不要改用 `Shift+Insert`**——Monaco 类编辑器（VS Code 聊天框、网页版代码
编辑器）会把 `Insert` 当成切换插入/覆盖模式，还会吞掉 Shift 修饰键，
表现为"粘贴失败 + 光标变成块状"。

> **时序参考区间**（业界实测）：窗口切换 50-200ms、焦点确认 20-100ms、
> 键盘模拟 10-50ms。任何一步偏差都可能导致粘贴失败，这也是「粘贴延迟」
> 这个配置项存在的原因。

**固定状态同样不抢焦点**：`show_panel` 在固定时必然走不激活路径。
置顶窗口本就在最上层，无需焦点即可被看到；抢焦点既打断用户输入，
又会让后续粘贴无法定位目标。

> **关于管理员权限**：以管理员身份运行时，Windows 的 UIPI 机制会阻止
> 普通权限的目标进程与提权进程互抢焦点。此时粘贴到普通程序（记事本、
> 浏览器等）可能失败。这是系统的安全边界，无法在应用层绕过。
> 建议以**普通权限**运行；仅在需要粘贴到其他提权程序时才用管理员启动。

### 排查粘贴失败

日志（`%APPDATA%\com.quickclip.app\quickclip.log`）会记录完整链路：

```
前台窗口追踪钩子已安装
粘贴 → notepad.exe: 焦点已在目标窗口，无需抢占      ← 不夺焦点模式的常态
粘贴 → notepad.exe: 抢占焦点 true                    ← 需要补救时
粘贴完成 → notepad.exe
```

若看到 `粘贴：目标未获得焦点，第 N 次重试`，说明目标程序响应慢，
可在设置里调大「粘贴延迟」；若看到 `粘贴已中止`，则本次为避免误输入而主动放弃。

## 配置项说明

配置存于 `Configs/ClipConfig.json`，亦可通过界面右上角**齿轮按钮**修改。

> 配置字段采用 **camelCase** 命名。若你的配置文件是早期版本生成的（字段为首字母大写，如 `Hotkey`），程序会自动归一化读取，不会丢失设置；保存后会以新命名重写。

> **历史字段**：早期版本曾提供 `pasteWithNewLine`（粘贴时追加换行）、
> `enableEdgeHide`（边缘自动隐藏）、`useFloatingOrb`（悬浮球）、
> `doNotRemindOnClear`（清空不提醒）、`itemSpacing` / `clipListSpacing`（间距）、
> `autoHideSearchBox`（自动收起搜索框）等字段。它们均未接入实际行为，
> 已从程序与本文档中移除。`ClipConfig` 带 `#[serde(default)]`，
> 老配置文件里的这些残留键会被忽略而不会导致读取失败，保存时自然被清掉。

| 字段 | 类型 | 默认值 | 说明 |
|---|---|---|---|
| `hotkey` | string | `"Alt+V"` | 全局唤出快捷键，须含修饰键（Ctrl/Alt/Shift/Win） |
| `theme` | string | `"dark"` | `dark` / `light` |
| `fontSize` | number | `13` | 界面字号 |
| `maxItemCount` | number | `500` | 历史最大条数 |
| `maxItemSize` | number | `20000` | 单条最大字符数 |
| `allowDuplicateCopy` | bool | `false` | 是否保留重复内容 |
| `ignoreWhiteSpace` | bool | `true` | 忽略纯空白内容 |
| `usingNumberKeyToPaste` | bool | `true` | 数字键直接粘贴 |

## 已知限制

- **仅支持 Windows**：平台层依赖 Win32 API，未做跨平台适配。
- **管理员权限程序**：若目标程序以管理员权限运行，而本程序非管理员，Windows 的 UIPI 机制会拦截按键投递，表现为粘贴无反应。解决办法是让本程序以管理员身份运行。
- **图片检索**：图片内容不做 OCR，仅按文件名参与搜索。
- **大列表性能**：当前为全量 DOM 渲染。历史条数超过约 2000 条时建议引入虚拟滚动。
- **收藏分组需手工建**：文件夹节点可由后端创建（`FavorItem.is_folder`），但界面尚未提供新建分组的入口，目前只能收藏到根级。
